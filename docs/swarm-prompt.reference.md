Model routing for spawned swarm agents. Pass `model` (and optionally `effort`)
when spawning. Run `swarm list_models` to see routes; prefer the ones below,
because "listed" does not mean "working".

Route by what the worker will actually DO:

- **Long-horizon / unsupervised / multi-file / unfamiliar codebase:**
  `claude-sonnet-4-6`. MEASURED 2026-07-30, overriding the benchmark table
  below: two `dashscope:glm-5.2` workers given a read-only code-mapping task
  produced ZERO output in 8+ minutes and had to be killed, while Sonnet
  finished the same task in ~60s. GLM-5.2 benchmarks well and is unusably slow
  on this route. Use `openai-compatible:dashscope:glm-5.2` only as a fallback.
- **Default general coding worker, well-specified task:** `deepseek-v4-pro`
  (SWE-bench Verified 80.6, cheapest capable; keep the task concrete).
  MEASURED: consistently 20-40s per bounded task, answers correct. The bare
  pin resolves to api.deepseek.com with DEEPSEEK_API_KEY, verified in the
  request log, so it is safe to write without a profile prefix.
- **Bulk reading / summarization / mechanical edits:** `deepseek-v4-flash`
- **Cheap classification / extraction / test scaffolds:** `qwen3-coder-flash`
  or `gpt-5.4-nano`
- **UI / frontend / visual work:** `kimi-k3` (Frontend Code Arena #1),
  else `kimi-k2.7-code`
- **Research / synthesis with citations:** `gpt-5.5` with `effort: "low"`
- **Hard terminal/agent reasoning cheap models failed:** `gpt-5.3-codex`
  (the ONLY surviving codex route), else escalate to the coordinator.
- **Second opinion / adversarial review:** pick a DIFFERENT family than wrote
  the code. Same-family review shares blind spots.

Hard rules:

- NEVER spawn workers on Fable, Mythos, or Opus models. That is coordinator-only
  quota. `claude-sonnet-4-6` is the ONE exception, and only for the long-horizon
  case above, because the cheap route for it measurably does not work; prefer a
  cheap model whenever the task is bounded enough for one.
- NEVER route to a bare `glm-*` (Z.AI, out of balance). Use `openai-compatible:dashscope:glm-5.2`.
- Prefer the two-segment `<profile>:<model>` pin (e.g. `deepseek:deepseek-v4-pro`)
  over the three-segment `openai-compatible:<profile>:<model>` form. Both work as
  of c421b8c2b, but the three-segment form silently billed the wrong endpoint
  before that fix, so the short form is the safer habit.
- NEVER route to a `*-codex` other than `gpt-5.3-codex`; the rest are 404.
- NEVER route to `ZHIPU/*`, `kimi/*`, `MiniMax/*` or `vanchin/*` aliases on
  dashscope: "product is not activated".
- Do NOT give DeepSeek an open-ended "migrate the repo and tell me when done"
  task. It scores lowest of the open weights on unsupervised agent benchmarks
  and reports false completion. Give it bounded, verifiable work.
- Do NOT use Kimi for cheap bulk work (cost + looping risk).
- Fallback chain if a route is unavailable:
  `openai-compatible:dashscope:glm-5.2` -> `deepseek-v4-pro` -> `qwen3.7-max` -> `MiniMax-M3`.

Prompting rules that matter more than model choice:

- Always pass `label` when spawning (e.g. `label: "api reviewer"`).
- Demand EVIDENCE, never a claim: require pasted command output, diffs, and
  test results. Every model in this list will otherwise report success on
  unfinished work. MEASURED: 38 worker reports carried a confident `validation`
  string describing commands the session never ran, including one reading "All
  7 steps executed with real command output" from a transcript with zero tool
  calls. This is not a cheap-model problem: a Sonnet worker did 16 tool calls of
  real research and then reported "Findings with file:line evidence for each
  item" while attaching no findings at all.
- Use `output_schema` when you need specific fields rather than a summary. The
  worker is then told its FINAL message must be one JSON object matching that
  schema, so you get a machine-checkable answer instead of prose that merely
  claims the answer exists. Include an evidence field (e.g.
  `commands_run: [string]`) so the claim is comparable to what actually ran.
- Reports whose `validation` asserts commands that the worker's tool log does
  not show are now annotated "Unverified" automatically, and logged under
  `[swarm:report-audit]`. Treat that marker as unreviewed work, not as a
  finished result.
- State the constraints the worker cannot infer (dependency limits, files it
  may not touch, gates it must not weaken). Workers do not read your mind and
  will happily "fix" a failing gate by deleting the check.
- Tell the worker explicitly NOT to weaken tests or gates to make them pass.

Structure guidance:

- In normal and light-swarm mode, only the root session may spawn agents.
  Workers complete their assigned task directly and report back.
